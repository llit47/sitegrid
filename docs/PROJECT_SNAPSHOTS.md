# PR17 / M10 — autoryzowany odczyt offline

M10 pobiera **jeden wybrany projekt** i udostępnia potwierdzony, kompletny snapshot wyłącznie do odczytu. Nie implementuje kolejki M11, synchronizacji/konfliktów M12 ani godzin M13. Pełna bramka MVP offline-first pozostaje nieukończona.

## API i limity robocze

`GET /api/organizations/:id/projects/:projectId/snapshot` ma `Cache-Control: no-store`. To osobny moduł serwera `project-snapshots/`. Sesja wyznacza stabilne UUID konta; nowe pole `user.id` w `/api/auth/session` nie zastępuje serwerowej autoryzacji. Email i parametry klienta nigdy nie określają aktora. Dotychczasowe członkostwo, status firmy/konta, przydział i RLS obowiązują bez wyjątku dla administratora platformy. Archiwum zachowuje dotychczasowy dostęp do odczytu.

Autoryzacja oraz wszystkie odczyty współdzielą jedną transakcję PostgreSQL **REPEATABLE READ READ ONLY** i lokalny kontekst aktora/firmy/projektu. Projekt, kontrahent i zadania przedstawiają ten sam moment bazy. Cofnięcie dostępu po rozpoczęciu transakcji nie zmienia już tego momentu; kolejna odpowiedź sprawdza nowy stan. Standardowe transakcje mutacji pozostają READ COMMITTED.

Envelope format 1 zawiera `complete: true`, scope `{accountId, organizationId, projectId}`, UTC `generatedAt` serwera i `expiresAt` (+24 h), `taskAccess: none/own/project`, projekt (id/nazwa/opis/status/wersja/createdAt/updatedAt), minimalnego kontrahenta `{id,name,status}|null` oraz zadania (id/tytuł/opis/status/wersja/czasy/nazwa wykonawcy, jeśli dostępna w dotychczasowym zakresie). Nie zawiera katalogu kontrahentów, rosteru pracowników, cookies, haseł, tokenów lub CSRF. Administrator firmy z uprawnieniem do samych metadanych otrzymuje `taskAccess: none` i pustą tablicę; pracownik tylko własne zadania; kierownik/brygadzista własny dotychczasowy przydział projektowy. Obcy/niedostępny projekt nie ujawnia rekordów.

**Provisional product limits:** maksymalnie **500 autoryzowanych zadań**, plus 1 projekt i najwyżej 1 kontrahent (**502 rekordy**); cała odpowiedź JSON maksymalnie **2 MiB = 2 097 152 bajty UTF-8**. Odczyt LIMIT 501 wykrywa przekroczenie; nie obcina danych. Przekroczenie któregokolwiek limitu daje **413** z `code: snapshot_limit` i polskim komunikatem, bez znacznika kompletności. Te konserwatywne wartości są wyborem implementacji M10, nie wcześniej zatwierdzonymi limitami produktu.

`integrity` zawiera SHA-256 kanonicznego JSON body (klucze obiektów posortowane, bez samego integrity), długość tego body UTF-8 i liczbę rekordów. Klient sprawdza dozwolone pola, wersję, kompletność, UUID zakresu, daty/statusy/wersje, unikalność zadań, liczby, rozmiar i digest. Hash wykrywa uszkodzenie; **nie jest podpisem autoryzacyjnym**. Uprawnienie pochodzi z pobrania bezpośrednio z uwierzytelnionego API, bez HTTP cache, w kontekście świeżo zweryfikowanego konta.

## IndexedDB i atomowość

Nazwa partycji pozostaje `sitegrid-project-<konto>-<firma>-<projekt>`, UUID małymi literami. **Schema v2** zachowuje store `metadata` i dokładnie ten sam rekord `owner` format 1. Jawna migracja **1 → 2** weryfikuje właściciela i dodaje out-of-line store `confirmed`; 0 → 2 tworzy oba. Nie usuwa/nie czyści innych stores, w tym przyszłych kolejek/szkiców. Nieobsługiwany nowszy schemat, błędny właściciel lub struktura powodują błąd, bez resetu danych.

Jedyny rekord `confirmed/snapshot` zawiera format lokalny 1, generation konta, lokalny czas rozpoczęcia autoryzowanego pobrania i cały zweryfikowany envelope. Jedna transakcja zastępuje cały rekord; sukces dopiero po COMMIT. Brakujące zadania z nowego kompletnego snapshotu znikają. Zapis nie dotyka metadanych, przyszłych kolejek ani szkiców. Starszy lub równoczesny timestamp snapshotu nie zastępuje zapisanego ani nie odnawia okresu dostępu; równoległa zmiana rekordu przerywa zapis. Przerwany download, malformed JSON, walidacja, quota i abort zachowują poprzedni kompletny rekord oraz jawny błąd odświeżenia. Nie ma częściowego „gotowe”. Uchwyty są zamykane i odrzucane przy zmianie kontekstu, odmontowaniu/anulowaniu i versionchange.

Osobna baza `sitegrid-offline-access`, schema 1/store `access`, zawiera tylko UUID ostatnio zweryfikowanego konta, losową generation, katalog dopuszczonych partycji i najwyższy zaobserwowany czas urządzenia. Anonimowy rekord z accountId NULL i pustym katalogiem zachowuje nową generation jako barierę przeciw opóźnionym odpowiedziom sprzed logout. Nie zawiera danych sesji ani treści projektu. Wpis katalogu przed zapisem nie oznacza gotowości: odbiorca wymaga dodatkowo kompletnego rekordu z pasującym właścicielem/generation i ważnym okresem dostępu. Niepowodzenie katalogu poprzedza i zatrzymuje zastąpienie snapshotu.

## Tożsamość, ważność i unieważnianie

Polityka M10: **24 godziny** od autoryzacji potwierdzonej przez serwer dla każdego snapshotu. Siedem dni z architektury pozostaje wcześniejszą, niezatwierdzoną propozycją maksimum. Klient liczy upływ od lokalnego początku requestu (konserwatywnie uwzględnia czas pobierania), sprawdzając serwerowy przedział 24 h. Cofnięcie zegara względem czasu zapisu lub lokalnego high-water powoduje odmowę. Przywrócenie sieci wymaga świeżej sesji; wykryta zmiana zegara/konta nadaje nową generation, bez automatycznego pobrania projektów. Zmieniony klient/profil/administrator urządzenia może obejść lokalną kontrolę zegara; to nie ochrona kryptograficzna urządzenia.

Zamknięcie PWA zachowuje ważne snapshoty i ostatnio zweryfikowany zakres. Offline restart nie używa emaila, URL ani dowolnego wyboru UUID do odblokowania danych; wymaga lokalnego katalogu i generation utworzonych po online verification. Bez nich, po wygaśnięciu lub uszkodzeniu — brak danych, wymagane online reauthentication. Przełączenie przygotowanej firmy offline jest jawne i czyta tylko partycje wybranej firmy tego konta; nie pobiera innych projektów.

Przed login/logout klient ustawia **wyłącznie odmowny**, niesekretny cookie `sitegrid-offline-denied=1` i unieważnia katalog konta. Cookie nie przechowuje tożsamości ani danych i nie może nadać dostępu. Jeśli IndexedDB odmawia czyszczenia, znacznik pozostaje przez restarty: offline fail closed, UI informuje o blokadzie, online pozostaje dostępne. Jeśli nie da się utrwalić nawet znacznika, zmiana konta zostaje zatrzymana. Tylko ponownie potwierdzona sesja i udany zapis nowej generation mogą usunąć znacznik. Opóźniona odpowiedź sesji ze starej generation jest odrzucana. Wylogowanie niezawodnie unieważnia, lecz nie obiecuje fizycznego wymazania bajtów każdej starej partycji; nieaktywne generation nie są odczytywane. Usunięcie danych witryny usuwa je fizycznie.

BroadcastChannel przekazuje wyłącznie sygnał invalidacji, bez danych konta; M10 dodaje niesekretny prefix fence przed historycznym sygnałem, aby zachować kompatybilność otwartych klientów M09. Sam historyczny sygnał bez prefixu konserwatywnie unieważnia dostęp lokalny M10; inne karty odmontowują widoki. Viewer co sekundę sprawdza katalog/ważność i przy powrocie do widocznej karty czyści widok przed sprawdzeniem (również bez BroadcastChannel). 401 blokuje konto, 403/404 zakres projektu/firmy; potwierdzony brak projektu na liście lub zadania w autoryzowanym odczycie unieważnia odpowiedni snapshot. Najpierw usuwany jest wpis dopuszczenia, następnie confirmed record. Błąd cleanup blokuje cały dostęp offline trwałym denial marker. **Nie ma remote wipe:** odcięte urządzenie nie wie o cofnięciu roli/przydziału aż do połączenia; stare uprawnienie ogranicza jedynie 24 h.

Wszystkie prywatne treści są wyłącznie w partycjach IndexedDB. Brak business data w Cache Storage, cache workera, localStorage, sessionStorage lub denial cookie. Lokalna izolacja nie chroni przed inną osobą korzystającą z odblokowanego profilu przeglądarki, kodem wykonanym z tego samego origin ani administratorem urządzenia. Profil/urządzenie wymaga blokady systemowej. Błąd IDB nie blokuje zwykłej pracy online; nie daje potwierdzenia gotowości offline.

## UI, wydania i odbiór

„Przygotuj offline” pobiera tylko wybrany projekt. „Gotowy offline” wymaga zweryfikowanego COMMIT **i dostępnej statycznej powłoki aktualnie aktywnego workera**. UI podaje liczbę zadań, czas, progres/anulowanie, błąd limitu i rozróżnia starszy zapis od nieudanego odświeżenia. Offline viewer pokazuje nazwę/opis, historycznego kontrahenta, uprawnione zadania/statusy/wykonawców i ostrzeżenie o możliwej zmianie na serwerze. Nie ma formularzy, komend, edycji, administracji ani obietnicy synchronizacji. Reconnect montuje istniejący świeży widok online bez replay.

PostgreSQL nadal **11**, bez migracji SQL. Standardowa paczka zawiera moduły snapshot API i kompletny build PWA. Update workera nadal czeka na zamknięcie kart, czyści tylko statyczny cache SiteGrid i nie dotyka IndexedDB. Rollback do klienta M09C/schema IDB v1 nie otworzy v2 i nie kasuje danych; jego funkcje online nadal działają. Powrót do klienta M10 odzyskuje snapshoty, jeśli lokalny dostęp jest nadal ważny. Cached M10 client wobec starszego API bez stable user.id blokuje offline zamiast wywodzić konto z emaila; bajty pozostają, lecz po unieważnieniu lokalnego dopuszczenia wymagane jest ponowne przygotowanie. Nie wykonujemy downgrade IDB ani PostgreSQL. Backup serwera nie obejmuje urządzeń. [Wydania](RELEASES.md).

Manualny odbiór na fizycznym Android Chrome i iOS Safari/Home Screen, produkcyjny HTTPS (automatyczny mobile viewport nie zastępuje urządzeń): przygotować projekt pracownika i metadata-only administratora; zamknąć/restartować PWA offline; sprawdzić autoryzowany zakres/status/kontrahenta i brak zapisów; przełączyć dwie przygotowane firmy; sprawdzić wygaszenie po 24 h, zmianę zegara i usunięcie danych; przerwać odświeżenie/wyczerpać storage bez utraty starszego zapisu; logout/login innej osoby w dwóch kartach bez danych poprzednika; odebrać przydział online/offline i potwierdzić ograniczenie remote wipe; update/zgodny rollback i powrót M10 bez kasowania ważnych snapshotów. Zanotować wersje systemu/przeglądarki i wyniki. Fizyczne urządzenia i czysty Debian/systemd nie są zweryfikowane w tym PR.

Walidacja lokalna 2026-10-10: Node 24.21.0, PostgreSQL 17.11 z oddzielną nieuprzywilejowaną rolą runtime; `npm run check` **170/170**, w tym 8 testów snapshotów, zero pominięć. Sześć zestawów Playwright/Chromium przeszło (snapshoty, PWA, branding, projekty, kontrahenci, postęp), obejmując desktop/mobile, błędy storage, revocation i starsze sygnały klienta. Paczka produkcyjna Linux x64 i Python **56/56**, zero pominięć; syntax checks i `git diff --check` przeszły. Fizycznych urządzeń i czystego Debiana/systemd nie sprawdzono.
